# 日通 POC｜Prototype 功能設計方案

- 更新日期：2026-08-07
- 文件定位：依 2026-07-22 最新會議紀錄、目前 Prototype 與後續討論整理
- 使用方式：作為內部對焦與客戶需求釐清工具，不代表正式產品規格

## 1. POC 核心目標與成功定義

> **讓調度看得清、判斷快、排得進：在單一畫面掌握 91 台車的執行進度與可用空檔，快速找出異常與插單機會，在不影響既定牛奶便的前提下，提高每台車的有效利用率。**

內部可將目標理解為「盡可能榨乾每台車的產值」：看清楚每台車正在執行什麼、接下來要去哪裡、哪些時段仍有利用空間，讓既有車輛可承接更多合適任務。

對客戶溝通時，建議使用「提升車輛使用效率與調度判斷速度」，避免把 POC 說成已能自動最佳化或取代調度。

### POC 要驗證的三件事

1. 是否能讓調度在單一畫面快速掌握 91 台車的執行狀況。
2. 是否能提早辨識需要關注的車輛與站點，減少逐車查詢與人工判斷。
3. 他項業務出現時，是否能協助調度找出候選車輛與安插位置，提升車輛空檔利用率。

## 2. 客戶現況與核心痛點

依 2026-07-22 最新會議紀錄：

- 現有天眼系統可以查看 GPS 位置，但無法直接判斷車輛是否準時到離站。
- 確認一台車的狀況約需 3–5 分鐘；91 台車無法在單一畫面快速掌握。
- 地圖上的客戶據點過於密集，車輛位置與任務脈絡不易辨識。
- 每月有固定路線與站點計畫，但每日仍需人工整理、分區、分時段並分配車輛與司機。
- 車輛、司機、路線、趟次、GPS 與站點計畫目前尚未形成一致的即時監控視圖。
- 客戶期待具備延遲預警、路徑與站點視覺化，以及歷史運輸紀錄查詢能力。

## 3. 初版 Prototype 的提案方向

### 3.1 產品定位

「營運監控為核心，插單判斷為延伸」

- 營運監控：哪些車正在執行、哪些車需要注意、異常發生在哪個站點。
- 即時定位：車在哪裡、距離目標站點多遠、車輛與站點的空間關係。
- 插單輔助最：臨時訂單可由哪些車承接、適合插在哪兩個既有站點之間。
- 系統提供候選與客觀資訊，最終仍由調度確認。

### 3.2 核心設計假設

1. 監控主體先以「車輛」為主，一列代表一台車；便次與站點是車輛時間軸上的任務。
2. 時間軸是主視圖，因為使用者需要先判斷執行進度、前後任務與可利用空檔。
3. 地圖是輔助視圖，用於即時定位、確認站點與車輛距離，以及插單時比較空間關係。
4. 可能延遲的實際判斷主體是站點；車輛層級只彙整提示「此車有站點可能延遲」。
5. 他項業務不常駐佔用主畫面，以「待插單」入口進入獨立工作區。
6. 建立候選後不自動選中第一台車，避免被理解為系統已替使用者推薦。

## 4. 目前 Prototype 功能結構

### 4.1 營運監控

- 執行日與 30 秒自動更新提示。
- 總覽（91）、可能延遲、延遲的數字提示與篩選。
- 以車輛為列的時間軸，固定顯示車牌、司機、路線與便次。
- 任務區段顯示站點名稱；Hover 顯示司機、便次、地址與時間資訊。
- 狀態包含提前、準時、延遲與可能延遲。
- 現在時間線協助判斷已發生、正在執行與尚未開始的任務。
- 可切換「顯示原規劃」，在同列比較原規劃與實際執行。

### 4.2 可能延遲的資訊層級

- 總覽：顯示可能延遲的車輛數。
- 車輛固定欄：以橘色警示 Icon 表示此車至少有一個站點可能延遲。
- 時間軸站點：受影響站點維持中性底色，只增加警示 Icon。
- Hover／地圖資訊卡：揭露「N 個站點可能延遲」與相關站點資訊。
- 不另外建立一條「可能延遲任務」，避免把狀態誤認成另一個任務。

目前 Prototype 只示意概念，判斷門檻、計算方式與解除條件仍需確認。

### 4.3 即時定位

- 地圖預設收合，需要時由頁首「即時定位」展開。
- 地圖與時間軸上下相連，可拖拉調整高度，也可各自全螢幕查看。
- 點擊時間軸定位功能，地圖聚焦對應車輛或站點。
- 點擊地圖車輛，時間軸捲動並聚焦到對應車輛。
- Hover 車輛顯示車牌、司機、路線、便次、站點、地址與預計時間。
- 安排插單或站點定位時，以虛線連接車輛與目標站點，線段中央顯示直線距離。

直線距離目前只作為初步比較，不代表實際道路里程或行駛時間。

### 4.4 待插單與候選評估

- 右下角「待插單 N」為與地圖、時間軸平行的工作入口。
- 展開後，在 Nav 下方開啟 320px 右側 Panel，主視圖同步縮窄，不使用 Overlay。
- 已確認建立訂單與安排調度為不同角色：建單角色建立他項業務訂單，調度從待插單列表接續評估與安排。
- 點選一筆訂單後，進入「安排插單車輛」單筆詳情。
- 候選車輛卡顯示車牌、司機、預估工時，以及預計安插在前後哪兩個便次／站點之間。
- Hover 顯示「預覽」提示；點擊卡片後，時間軸與地圖同步聚焦候選車輛。
- 不自動選中候選，也不標示「推薦／不建議」。
- 使用者確認後，插單站點回到一般任務顯示邏輯，成為時間軸上的正式站點。

### 4.5 插單判斷資訊

初版優先呈現：

- 訂單指定時間與站點地址。
- 候選車輛與司機。
- 預估工時。
- 安插前一站：便次、站點、地址、預計完成時間。
- 插單站點：站點、地址、指定時間。
- 安插後一站：便次、站點、地址、預計開始時間。
- 地圖上的車輛位置、插單站點與直線距離。

「增加時間／里程、後續任務影響、容量與工時限制」若沒有明確資料來源與算法，不應在 POC 中假裝成精準結果；先列為後續確認項目。

## 5. 核心使用流程

### 日常監控

營運監控 → 以總覽／可能延遲／延遲篩選 → 查看車輛與站點 → 視需要展開即時定位 → 進一步處置

### 待插單

點擊「待插單」 → 選擇一筆訂單 → 查看候選車輛 → Hover 初步比較 → 點擊候選並同步預覽時間軸與地圖 → 確認插入

## 6. 狀態與用詞

| 用詞 | Prototype 暫定定義 | 顯示層級 |
|---|---|---|
| 提前 | 已完成站點的實際時間早於原規劃 | 站點 |
| 準時 | 已完成或執行中的站點符合原規劃 | 站點 |
| 延遲 | 已發生且實際時間晚於原規劃 | 站點，並彙整至車輛／總覽 |
| 可能延遲 | 尚未成為延遲，但依目前進度被判定需要關注 | 站點判斷，車輛彙整 |
| 原規劃 | 派車或站點原始計畫時間 | 時間軸比較 |
| 實際時間 | 已發生的到離站時間；提前顯示藍色（-N分），延遲顯示紅色（+N分） | Hover 詳情 |

## 7. 第一版 Prototype 範圍

### 本版已涵蓋

- 車輛時間軸營運監控。
- 原規劃與實際執行比較。
- 可能延遲與延遲的分層提示。
- 可展開、調整高度與全螢幕的即時定位地圖。
- 車輛、站點、時間軸與地圖的雙向聚焦。
- 待插單列表、候選車輛比較、預覽與確認插入。

### 本版暫不涵蓋

- 建單角色使用的正式訂單 Key in 與欄位驗證。
- AI 自動排程或最佳車輛推薦。
- 正式 ETA、道路里程與延遲預測演算法。
- 司機 App 通知、接單與執行回報。
- 完整歷史紀錄頁、報表與分析。
- 正式資料寫入、權限、多人協同與稽核紀錄。

## 8. 初版 Prototype 的討論重點

1. 一列一車的監控視角是否符合調度的判斷習慣？
2. 車牌、司機、路線、便次、站點與時間是否足以辨識車輛及任務？
3. 可能延遲採「站點判斷、車輛彙整」是否合理？
4. 時間軸為主、地圖按需展開的資訊比例是否合適？
5. 待插單作為調度角色的獨立工作入口，而非時間軸附屬功能，是否符合實際操作？
6. 候選卡、時間軸與地圖提供的資訊，是否足以支持人工判斷？
7. 歷史紀錄真正需要解決的是查找、回放、稽核，還是績效分析？

## 9. POC 驗證完成標準

- 調度能在短時間內找出需要注意的車輛與站點。
- 使用者能理解時間軸、地圖與狀態提示之間的關係。
- 使用者能說明自己如何判斷一台車是否適合承接插單。
- 團隊能列出正式資料與算法仍缺少的項目。
- 客戶確認 Prototype 的資訊架構可以作為後續 POC 深化方向。
