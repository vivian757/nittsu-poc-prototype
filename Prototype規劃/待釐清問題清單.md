# 日通 POC｜關鍵待釐清問題

- 更新日期：2026-08-14
- 用途：整理會影響 POC 資訊架構、判斷規則與操作流程的關鍵問題
- 原則：先列待釐清問題與 Prototype 假設，已確認內容集中放在文件最下方

## 1. 先跟內部對齊

| ID | 關鍵問題 | 需要的結論 |
|---|---|---|
| I-01 | POC 最終要證明什麼？ | 明確定義成功指標，例如調度找出異常、完成他向業務指派所需的時間與步驟 |
| I-02 | POC 要驗證到介面流程、規則計算，還是實際資料串接？ | 確認技術驗證範圍、模擬與正式資料的邊界，以及歷史功能是否納入本輪 |

## 2. 待釐清

| ID | 主題 | 關鍵問題 | 影響範圍 |
|---|---|---|---|
| C-01 | 營運監控 | 以車輛為主體是否符合調度習慣？車牌、當前司機、客戶／路線、便次、站點與時間是否足以辨識任務？除「總覽、執行中、異常」外，日常查看是否還需要其他分類？ | 固定欄資訊、篩選與主畫面層級 |
| C-02 | 時間差判斷 | **過往 TMS 專案經驗提醒（非日通現行系統規則）**：當時電子圍籬判斷會設定緩衝容許時間，並以單一時間欄位產生「提早、準時、延遲」其中一個狀態；即使規則較單純，仍花費許多時間釐清。本案已確認以最新已發生事件決定 Bar 狀態，仍需確認電子圍籬進／離場事件的去雜訊方式、提早／準時／延遲容許值、缺漏或重複事件如何處理。 | 狀態門檻、異常計數與電子圍籬資料品質；過往經驗僅作為釐清風險提醒，不代表客戶需求或目前系統邏輯 |
| C-03 | 異常 Filter | 「異常」要整合哪些狀況？目前是否只收斂為當前任務延遲，或也包含未出車、異常停留、偏離路線、GPS 中斷與任務未回報？計數單位是車輛還是任務？ | Filter 數字、車輛層級提醒、異常詳情與處置入口 |
| C-04 | 牛奶便／他向業務車輛 | 他向業務車與牛奶便固定車是否為完全分開的車池？是否存在臨時共用、跨時段接續或其他例外？ | 可用車輛範圍、時間軸資料、車輛空檔與候選邏輯 |
| C-06 | 他向業務指派 | 已確認以訂單實際工時在指定時段內尋找可容納的起始時間，並掃描值班司機。仍待確認技能、載重、法定工時、前後任務交通時間與完全人工指定的正式規則。 | 候選生成、不可指派原因、工時與車輛條件 |
| C-07 | 後續任務銜接不足 | 已確認先完成插單，再提醒並引導批次變更後續便次司機。仍待確認「銜接時間不足」的正式門檻、交通時間來源，以及稍後處理後的待辦期限與升級機制。 | 警示門檻、待辦管理與排程計算 |
| C-08 | 時間軸／空檔定義 | 已確認候選必須容納訂單實際工時、與前一任務至少相隔 30 分鐘，且不得晚於下一任務需抵達時間；最後一個便次後也可作為加班候選。仍待確認正式計算是否及如何納入前後行駛時間。 | 空檔長度、交通時間、候選資格與準時銜接 |
| C-09 | 改派後 ETA 重算 | 任務因原司機銜接不足而被標示「可能延遲」後，變更司機是否要立即依新指派重算 ETA？需確認重算所需資料是否包含新司機抵達固定車輛／交班點的時間、車輛位置與前序任務完成時間；以及重算期間、風險解除、仍可能延遲或無可靠 ETA 時各自如何呈現。 | ETA 狀態生命週期、警示解除條件、交班可行性與改派結果回饋 |

## 3. 目前 Prototype 工作假設

以下方向已用於 Prototype，但在上述規則確認前，不代表正式產品規格。

- 以車輛時間軸為營運監控主視圖，地圖按情境展開。
- 原規劃是主要基準；實際執行預設顯示，抵達與離站時間差放在次要視覺與 Hover 詳情。
- 「異常」目前只納入車輛當前最新任務的延遲；其他異常類型尚未納入。
- 他向業務暫採先選司機空檔、再搭配非固定便次車輛；系統提供候選但不標示最佳推薦。
- 時間軸上的「空檔」暫只依任務起訖時間計算，尚未納入前後站點的行駛時間。
- 後續任務銜接不足採「先完成本次指派，再提醒是否批次變更受影響的後續便次」。

## 4. 已釐清

| 主題 | 已確認內容 | Prototype 對應 |
|---|---|---|
| 角色分工 | 建立他向業務訂單與調度指派為不同角色；調度從「待插單」清單接續安排 | 「待插單」為獨立工作入口，不視為時間軸附屬功能 |
| 客戶現況 | 客戶目前沒有實際使用電子看板；現有系統廠商「天眼」曾提供示意圖，但未落地使用 | Prototype 是需求與提案方向的驗證工具，不應描述成既有流程的直接改版 |
| 時間差基礎 | 時間差主要針對牛奶便；每一趟次都有原規劃開始與結束時間，並以電子圍籬進／離場事件取得實際時間 | 原規劃為基準，實際執行呈現抵達與離站資訊 |
| 抵達與離站 | 抵達與離站時間差都需要掌握；Bar 顏色以最新已發生事件為主：尚未離站時看抵達狀態，離站後改以離站狀態呈現；準時不需在資訊卡重複列出 | 主時間軸顯示目前最新狀態，Hover 僅補充提早或延遲的抵達／離站差異 |
| 營運監控排序 | 總覽中的車輛依「異常 → 執行中 → 其他」排序；牛奶便車輛排在他向業務車輛之前，無當前任務的車輛置底 | 主畫面先呈現需介入與正在執行的車輛，降低調度掃描成本 |
| 異常收錄規則 | 當前最新執行的任務站點有延遲才列入異常；若最新離站為準時或提早，則不納入異常。後續站點的 ETA 風險另以「可能延遲」呈現，不等同已發生延遲 | 異常 Filter 聚焦已發生且仍影響當前行程的延遲；ETA 使用淺橘色預警 |
| 時間軸結構 | 站點區塊代表原規劃；站點間空白即為行駛區間，不需另畫行駛任務；實際執行不會超過現在時間 | 「顯示實際狀況」預設開啟，實際線疊在原規劃下方 |
| ETA 可能延遲 | 經 ETA 判定為可能延遲的站點，時間軸任務區塊整塊使用淺橘色呈現 | 與已發生延遲的紅色狀態區隔，並保留文字或圖示輔助辨識 |
| 地圖使用時機 | 調度會在臨時訂單、司機回報狀況、客戶反映尚未看到車，以及直覺察覺異常時查看定位 | 時間軸維持主視圖，地圖由車輛、站點或訂單入口按需定位 |
| 兩種業務的指派單位 | 牛奶便的資料層級為「固定車輛 → 便次 → 多個站點」，司機綁定整個便次；他向業務則由司機、車輛綁定單筆訂單，沒有便次概念 | 牛奶便以便次為改派單位；他向業務維持單筆訂單指派，時間軸資訊以「他向業務＋客戶名稱」辨識 |
| 牛奶便固定車 | 原牛奶便使用的固定車輛不提供更換，可能涉及載貨及工廠需預先掌握車牌 | 變更牛奶便指派時只更換司機，車輛唯讀；他向業務插單不直接改動牛奶便車輛 |
| 牛奶便便次結構 | 同一路線不同便次原則上重複相同站點組合，站點停留與站間時間固定或接近；便次間保留該路線相對固定的空檔 | 時間軸以成組且重複的站點呈現各便次，避免任務重疊或分布過度平均 |
| 牛奶便一般改派 | 點擊任一站點只是操作入口，實際變更該站點所屬便次的司機，並同步套用便次內全部站點；已完成便次不可改派，執行中便次需另走交接／異常流程 | 時間軸 Highlight 整個便次；Panel 顯示路線、便次、完整時段、站點數、固定車輛與目前司機，確認後一次更新整個便次 |
| 牛奶便可指派司機 | 變更牛奶便指派時，候選先從當日跑他向業務的司機中篩選，且該司機必須能完整承接目標便次；不以單一站點可用作為判斷 | 「可指派司機」只列出他向業務司機並提供查看其既有時間軸；預覽不改寫時間軸左側目前司機或 Hover 司機，確認後才正式更新 |
| 司機空檔 | 司機空檔可位於兩個任務之間，也可位於當日最後一個任務後方；上下任務皆無屬於當日未排班，不稱為空檔。沒有下一任務時可能代表已下班，需顯示今日工時並視為加班候選 | 空檔卡顯示上一任務、下一任務與報到／今日工時資訊，再搭配可用車輛 |
| 插單候選空檔 | 系統以訂單實際工時在指定時段內尋找可容納的起始時間，不要求整個指定時段皆無任務；與前一任務相隔 30 分鐘以內、或訂單結束晚於下一任務需抵達時間者，不納入候選 | 同時掃描值班司機與可用他向業務車輛；最後一個便次後若無下一任務仍可列為加班候選 |
| 指派預覽 | 選司機時聚焦其時段；選完車輛後才切換至該車輛並顯示站點預覽；更換司機會清除已選車輛與預覽 | 指定時段、司機空檔與站點預覽分層呈現 |
| 插單後續批次改派 | 插單先獨立完成；若造成牛奶便後續銜接不足，再從第一個受影響便次起，批次更換原司機今日後續連續負責的便次，遇到既有司機交班點即停止 | 成功 Snackbar 後顯示銜接不足 Dialog；稍後處理須保留待辦警示，前往變更則以便次分組、車輛唯讀，批次更新一次成功或全部失敗 |
| ETA 不確定狀態 | 僅對確認受影響的後續站點顯示 ETA。若已有可靠 ETA，顯示預計抵達時間與預計延遲分鐘；若前站尚未抵達、無可靠 ETA，後續站點只顯示「可能延遲」，不標示分鐘數 | 可能延遲使用淺橘色任務區塊，與已發生延遲的紅色狀態區隔 |
| 實際執行時間邊界 | 實際執行資料只代表已發生事實，不會出現在「現在」右側；進行中的實際線最多貼齊現在 | 時間軸以現在線截斷實際執行，不把未來預估混入實際線 |
| 點呼表資料單位 | 同一天一位司機只會有一筆點呼表紀錄；尚未報到時，實際報到、最後更新時間與點檢者皆為空，內容顯示「尚未報到」；點檢者在完成審核後才寫入 | 未報到不可執行審核 CTA；已審核可切回未審核，列表與詳情維持同一筆司機日紀錄 |
