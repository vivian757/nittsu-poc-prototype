## 1. POC 範圍與核心目標

> **讓調度即時監控車輛的執行進度，快速掌握異常狀況，並找出可承接他向業務的車輛與安插位置，在不影響既定牛奶便的前提下，提高每台車的有效利用率。**

Notes 盡可能榨乾每台車的產值 

### POC 要驗證的三件事

1. 調度能否快速掌握車輛、便次與站點的執行狀況。
2. 系統能否幫助用戶快速找出需要關注的異常車輛與站點，減少逐車查詢。
3. 他向業務出現時，系統能否協助找出候選車輛與安插位置。

### 本輪範圍

| 納入 | 暫不納入 |
|---|---|
| 車輛時間軸營運監控 | AI 自動排程或最佳車輛推薦 |
 |
| 可能延遲、延遲與即時定位 | 司機 App 通知、接單與回報 |
| 插單(他向業務臨時插入牛奶便) | 完整 Key in、歷史報表與分析 |

已確認建單與調度為不同角色：建單角色建立他項業務訂單；調度從「待插單」清單評估並安排車輛。

## 2. 初版 Prototype 與提案方向

> **營運監控為核心，插單判斷為延伸。**

### 目前設計方向

- **以車輛為監控主體**：一列一車，顯示車牌、目前司機、路線與便次；站點任務呈現在時間軸上。
- **時間軸為主視圖**：掌握執行進度、前後任務、原規劃與實際差異。
- **地圖為輔助視圖**：需要定位或比較車輛與站點的空間關係時展開。
- **異常分層呈現**：站點判斷可能延遲／延遲，車輛與總覽彙整提示。
- **待插單為獨立入口**：調度選擇訂單後，再查看候選車輛與前後便次。
- **系統輔助、不替人決策**：提供候選與客觀資訊，最終由調度確認。

### Prototype 展示流程

1. 從總覽篩選可能延遲／延遲車輛。
2. 透過車輛時間軸查看站點進度及原規劃差異。
3. 視需要展開即時定位，確認車輛與站點位置。
4. 從「待插單」選擇訂單，比較候選車輛與前後便次。
5. 預覽時間軸與地圖後確認插入；插單成為一般站點任務。

目前插單暫定流程：

**建立訂單 → 排除排程衝突 → 顯示候選車輛與安插位置 → 比較時間軸／地圖 → 確認插入**

Prototype 暫定所有候選車輛皆對應訂單指定時段；候選差異在車輛位置、前後便次與任務銜接。是否允許系統建議其他時段，仍待確認。

## 3. 本次關鍵待釐清議題

| 主題 | Prototype 目前假設 | 本次需確認 |
|---|---|---|
| 整體／監控視角 | 以車輛為主體，便次與站點附著於時間軸 | 現場是否習慣先找車；「車輛為主、時間軸為主視圖」是否合理 |
| 整體／辨識資訊 | 顯示車牌、目前司機、路線、便次、站點與時間 | 現有資訊是否足以辨識車輛與任務；大量監控時還缺哪些資訊或篩選 |
| 插單邏輯／候選時段 | 先排除時間衝突，再比較車輛位置、前後便次與任務銜接 | 實際判斷順序與硬限制；候選是車輛／安插位置，還是也包含建議時段 |
| 插單邏輯／司機交接 | 插單可落在既有便次之間，車輛可能同時涉及司機交接 | 交接點的任務歸屬，以及法定工時、交接時間與 ETA 計算方式 |
| 異常告警／可能延遲 | 站點判斷可能延遲，車輛與總覽彙整提示 | 判斷門檻、資料來源、解除條件，以及是否需提供聯絡、註記或改派 |
| 異常告警／其他異常 | Prototype 目前聚焦可能延遲與已延遲 | 是否需納入未出車、異常停留、偏離路線、GPS 中斷或任務未回報 |
| 技術可行性 | 目前以介面、流程與設計假設驗證為主 | 可取得的排程、GPS、到離站及司機交接資料；規則可計算程度；模擬／串接方式與輸出邊界 |
| 其他／地圖與歷史 | 地圖先顯示直線距離；歷史紀錄尚未納入第一版 | 是否需要道路距離／行駛時間；歷史紀錄優先解決查找、回放、異常追查或績效分析 |
